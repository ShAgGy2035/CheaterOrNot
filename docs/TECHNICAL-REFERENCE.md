# Cheater or Not: Technical Reference

A simple Avalonia desktop app for Windows, macOS, and Linux. Enter a public individual SteamID64 or a supported HTTPS profile URL (including Leetify's `/app/profile/` and `/public/profile/` links) and press **Check player**, or import a local CS2 demo to preview its roster and load several players for checking.

**Public data and optional official APIs:** the app does not log in. Optional developer API keys may require provider accounts. Without optional API keys, Leetify's website adapter reads the anonymous JSON responses its public webpage uses; other pages can be rendered with bundled headless Chromium. This does not bypass website access restrictions. Local-only demo import sends nothing. **Analyze demo with Gemini** is the upload authorization: it prepares reconstructed clips and bounded requests, then sends all prepared video/audio/telemetry batches to Google without a second popup; footage is not anonymized. Raw demo files are never uploaded.

**This is an evidence-review tool, not a cheating detector.** Statistics cannot establish cheating, and there is no scientifically calibrated cheating probability. Do not use reports alone to accuse or penalize anyone.

## Run

The portable Windows x64 application is [publish/CheaterOrNot.exe](publish/CheaterOrNot.exe). The application includes .NET 10, native libraries, the Playwright driver, Chromium Headless Shell, and vendor notices. **Capture components are not redistributed with public release artifacts.** On first capture, the app downloads verified upstream CS Demo Manager, FFmpeg and extractor releases into its local `tools` folder. Steam and CS2 must already be installed. This is an unsigned development build; it does not bypass Windows security warnings. See [capture notices](src/CheaterOrNot/Assets/capture-tool-notices.txt). Never share private `tools/data`, imported demos or recordings.

Single-file distribution does not mean zero runtime files. .NET extracts executable/runtime/browser assets into its per-user extraction cache (normally `%TEMP%\.net` on Windows). Those assets are retained for subsequent launches; they are not downloaded player pages. If overriding `DOTNET_BUNDLE_EXTRACT_BASE_DIR`, use a short path on Windows to avoid extraction path-length limits. Keep the executable updated to receive bundled runtime/browser fixes.

Development remains at version 0.0.1. Ordinary builds are not separate releases. Update the same working executable, close it before replacing it, and do not generate additional publish folders or ZIPs for routine development.

The application uses a plain mint question mark on a transparent background. Editable artwork is in [question-mark.svg](src/CheaterOrNot/Assets/question-mark.svg). The Leetify logo is provider attribution only, not the app icon.

## Progress and results

The interface has **Final result**, **Evidence**, **Screening rules**, **API Keys**, and **Top Pro Players** tabs. **Several players can be checked in one run**: separate SteamID64s (or supported profile URLs) with spaces or commas, and the Final result becomes a batch summary ranking players by flagged indicator types and then account cautions (review priority, never a cheating probability), followed by each player's full report; Evidence holds each player's full source details. The **Report: Website / Demo** switch shows one report at a time in both tabs. A completed website check or demo import selects its own report, and you can switch back without rerunning anything. **Copy all** copies the selected report's current tab; **Save report** exports its Final result and Evidence only, excluding the request preview. **Copy preview** is a separate action. Each player's websites are checked with a fresh disposable browser session that is deleted before the report appears.

A valid **Check player** or **Check player with AI** clears the visible results and disables copying and saving while the website search runs. If the search is canceled or fails before a new website report is ready, the previously selected report returns. If the website report is already ready but the optional AI review fails, the new website report remains available. Invalid input does not clear anything.

Both demo options also clear the visible results once you select a file. Closing the picker leaves the previous report unchanged; canceling or failing the import restores it. A successful import replaces the previous demo report and clears its Gemini commentary and request preview. If Gemini fails or is stopped after the new demo imports, the new local report remains visible. The last website report stays available through the report switch.

Each results tab has a **Copy all** button that copies the complete text of that tab to the system clipboard after a check completes. The saved report contains both tabs; copying one tab does not copy the other.

## Local CS2 demos

Select **Import local CS2 demo**, then choose one uncompressed Source 2 `.dem` file. Import reads that file locally, on a cancellable background worker. It does not modify the recording, read `.dem.info` keys, upload anything, contact websites, or attach game processes. CS:GO/Source 1 recordings, compressed archives, and videos are not supported.

**Evidence** shows human SteamIDs observed on T/CT, including participants who later disconnected, plus neutral death-event bookmarks with demo ticks and parser timestamps. Bots and spectator-only accounts are excluded. Recorded names are not verified current Steam names; recordings can be edited, so roster identities are not authenticated by Steam. Events include warmup and other recorded phases, not a verified competitive-match sample. Timestamps use the parser's 64-tick demo timebase, not round or wall-clock time; use the demo tick for seeking in CS2 playback (for example `demo_gototick`).

Select **Use roster for checks** to replace the input with those IDs and clear old website results. Review/edit the list, then explicitly press **Check player** to send the selected IDs to the configured public websites/APIs. Importing alone leaves existing website reports unchanged. **Copy demo report** and **Save demo report** export local context separately; the normal **Save report** never silently includes a potentially unrelated demo.

Limits: 1 GiB per seekable recording, 128 human accounts, and the earliest 20,000 decoded death-event bookmarks (all decoded deaths are counted). A partial-footer warning means only the readable recording was imported; no full-match completeness is inferred. Damaged/incompatible files fail explicitly without replacing an earlier successful preview. Parser compatibility depends on the CS2 recording format and may need updates.

This uses the free MIT-licensed [demofile-net](https://github.com/saul/demofile-net) parser. [Parser and dependency notices](src/CheaterOrNot/Assets/demo-parser-notices.txt) are included in the executable and extracted under `Assets` with its runtime files. Demo events and optional AI commentary never change website screening coverage, flags, verdicts, or batch priority.

### Experimental local gameplay review

Import now measures **recorded view-direction changes at firearm shots**, not just deaths. The first review selector bookmarks a change of **at least 20 degrees in 3D viewing direction between adjacent demo ticks ending at a shot**. Yaw wrapping and near-vertical views use a direction-vector comparison, not naive angle subtraction. A repeated selection pattern means at least three selected shots across at least two recorded round numbers. These are unvalidated bookmark-selection rules, not calibrated cheating thresholds or probabilities.

Assessment requires finite positions/angles, alive human T/CT snapshots, the same round/pawn/lifetime, adjacent demo ticks, no more than 64 units of movement between snapshots, and no warmup, freeze or ended-round state. Bot-controlled rounds, missing previous snapshots, unsupported weapons and discontinuities are excluded, not passed. Firearm events are deduplicated by player/weapon/demo tick. Reports show decoded and assessed shot counts, selection counts and rounds per player, and the earliest 2,000 selected events with round/tick, canonical weapon, measured turn and movement. All selections are counted even after the retention limit.

Recorded entity angles are not raw mouse input or subtick commands. The nominal 1/64-second interval is not reaction time. Flicks, recoil, ordinary target switching and network/demo sampling can explain selections. This first selector does **not** establish enemy alignment, target acquisition, visibility/hearing, recoil compensation or assistance. No selected moments does not establish clean play. Local aliases (`Player01`, etc.) map to SteamIDs in the local report; they are not account identities.

**Telemetry-first review also includes data below that threshold.** Each recorded round/player row shows eligible firearm shots, assessed shots, mean and maximum assessed view change, the maximum's demo tick, total eligible kills/headshot kills/deaths, and separate firearm-only kill/death counts. Null angle/tick values mean no assessed shots, not zero turn. Round shot counts require an eligible, finite snapshot; global decoded-shot totals can additionally include excluded phases/samples. A separate timeline retains the earliest 2,000 eligible opposing-human kill events across recorded weapons, while round totals count all eligible events. Warmup, freeze/ended-round states, controlled-bot rounds, team kills and suicides are excluded. Events with an unrecognized weapon are retained as `unknown`; firearm-only counts still require a recognized firearm. Event ordering can exclude round-ending kills; these are not full scoreboard totals. Round numbers use rules state at each event and are not independently verified. No hit/miss, reaction-time, target-alignment, visibility, audio or recoil-control measurement is invented.

**Multi-tick shot windows** retain the earliest 2,000 eligible firearm shots, whether or not a bookmark fires. Each requests eight contiguous valid ticks before and eight after the shot (nominally 125 ms per side). The report shows actual coverage, 3D net/path turn and samples of tick offset, recorded pitch and yaw relative to the shot. Path turn sums adjacent 3D turns; it is not an aim-smoothness metric. Gaps, invalid snapshots, phase/round/pawn/lifetime changes and movement discontinuities stop a side. Missing coverage remains partial, with null turn values if no ticks were covered on that side. Same-tick post-shot snapshots use the last observed update, while the shot snapshot is kept as recorded at WeaponFire.

The importer also retains the earliest 2,000 eligible opposing-human firearm **health-damage callbacks** and counts all eligible callbacks. Same-tick callbacks are not collapsed because they can be shotgun pellets. Shot-window context links retained damage/death events from the same attacker, recorded round and canonical weapon within 0-8 ticks after the shot. These are temporal associations, not bullet attribution, hit rate or measured reaction time. A retained-event ID lets the AI recognize an event referenced by several windows; links must not be added as unique hits/kills. Same-tick ordering is unknown. A 90-degree turn over eight ticks can avoid the 20-degree single-tick bookmark entirely: no bookmarks does not mean no flicks or normal/consistent aim. No validated normal-play baseline is supplied.

**Longer engagement context and coverage audits:** eligible same-player/round/pawn/lifetime/team/weapon shots are grouped when no more than 32 ticks apart, with a maximum 256-tick first-to-last-shot span. Invalid or discontinuous snapshots split groups. Retained sequences request 32 contiguous ticks on each side (nominally half a second), with actual coverage, full-sequence net/path turn, relative movement and shot snapshots. The first and latest groups per player/round are retained, at most two per pair and 2,000 globally; later pairs can lack examples once the cap is full. Counts continue for every eligible observed player/round, including nonfiring players and omitted groups. Observed ticks are not full-round duration or measured seconds. Grouping and retention are context selectors, not new cheating rules.

At each eligible shot, geometry compares the firing view with recorded eye-position proxies for same-tick, alive opposing humans. It selects the **smallest angular separation**, not the nearest enemy by distance, an intended target or a hitbox. Eye positions use recorded origin plus finite view offset (positive Z at most 128 units, bounded X/Y); missing offsets are never replaced with an assumed player height. Reports disclose usable/observed opponents, angle/distance, movement since the previous valid adjacent tick, minimum round eye angle and geometry coverage. Incomplete geometry can coexist with a successful measurement; missing values are null, not zero. Coordinates sent to Gemini are relative, not absolute map locations. None of this establishes line of sight, smoke/occlusion, audio, target acquisition, recoil control or reaction time. **Precise geometry-to-playback comparison remains a separate validation step**; numerical/parser checks and successful video capture do not replace it.

### Local video capture and component updates

After importing a demo, select **Advanced video tools**, review the bounded plan, then **Capture review clips locally**. The plan creates one attacker-POV clip for every retained eligible human-vs-human kill, across all recorded weapons, including knife/utility events. Each clip includes up to two seconds before and after the kill and ends before the attacker's next recorded death in that round. CS Demo Manager's native CS2 recording plugin renders 1280x720, 30 fps; X-ray and player voices are requested off and game audio on. These selections are not suspicious-player rankings.

Close any existing CS2 session first. Capture uses `-insecure` offline playback, temporarily integrates the upstream plugin with the game installation, and must not be used for matchmaking. One clip is produced per retained kill (up to 2,000); the app checks the estimated raw-frame disk requirement before starting, which can be very large for full matches. CS2 startup can take several minutes. Do not start another game while capture is running.

**Stop after current step** is deliberately not immediate termination: the upstream CLI delegates work to a separate service and does not provide a cooperative cancellation signal. Local indexing finishes before a requested stop prevents game startup. Once recording starts, recording/encoding and game cleanup finish before stopping; the app does not accept a completed review result after a stop request. Closing the window also waits for this safe boundary. A step exceeding 20 minutes fails explicitly and warns that its background service may still be active; this is not reported as successful cancellation.

The original demo is held read-only and copied into a private capture working directory; upstream playback sidecars are generated beside that copy, not beside the original. Successful capture removes the working demo. Failed/canceled attempts can leave partial files and a private copy for inspection. Output lives beside the real executable under `review-videos`; the local manifest maps each MP4 to its requested SteamID/alias, round and nominal ticks. Every clip must match its expected filename, resolution, 30-fps rate and duration (within 0.35 seconds or 10% of its nominal range). Audio-stream presence is reported, not silently assumed. Capture maintains a separate local index/database under `tools/data`; its service shuts down after becoming idle.

**Open output folder** opens the current attempt's folder after capture. Reopening the window or app restores access to the saved `review-videos` parent folder, including any partial attempts; folder availability alone does not mean an attempt succeeded.

**File checks are not footage-content verification.** Inspect the spectator HUD name against the local roster, not a dropped weapon's original-owner label. Demo-reconstructed views are not original player video; exact frame-to-tick alignment, raw mouse input, missing subtick commands and precise reaction/target-acquisition timing are not recovered. The HUD, chat, avatars and names can remain visible. Capturing clips does not establish cheating or clean play and does not change website results or Gemini commentary.

Capture alone never sends footage. **Analyze demo with Gemini** always makes a fresh capture in a unique folder; verified prior captures for the exact same source demo are replaced only after every new clip verifies, and captures for other demos are preserved. If fresh capture fails, the older same-demo capture remains. Prepared clips are sent automatically in bounded batches (at most ten clips and 12 MB of video per request). Selecting **Analyze demo with Gemini** is the upload authorization; selecting **Send all prepared batches** is the corresponding authorization in the advanced window. The UI still discloses the destination, footage privacy, quota/cost implications, and batch counts before the workflow is started. Each batch must return exactly one valid observation per supplied clip; a failed/invalid batch stops the workflow, and the app does not present a combined completed review unless every batch succeeds. Transient 502/503/504 responses receive bounded retries, with no model fallback. Advanced separate video and telemetry-only controls remain available.

The **Maintenance** section of **Advanced video tools** is collapsed by default. **Check component updates** queries official GitHub release metadata. **Update capture tools** downloads SHA-256/size-verified CS Demo Manager and FFmpeg 8.1-line archives, extracts them without running a system installer, smoke-tests candidates and atomically switches a relative manifest. Failed candidates do not replace the active manifest; older component directories remain available. **Repair matching browser** installs this app's pinned Playwright Chromium revision, not an arbitrary newest browser. New browser-engine revisions require an app/Playwright update; no app-binary update service is configured. Downloads occur only after a user action, never on startup. If Analyze or local capture detects missing or incomplete tools, it downloads the verified components automatically and reports progress in the existing workflow; no separate setup dialog is required.

The native desktop E2E driver is [VideoDesktop.e2e.js](scripts/VideoDesktop.e2e.js), using the same Computer Use runtime as the Gemini desktop test, not browser Playwright. After loading it, call `begin(target, authorizedDemoPath)`, `selectDemo()`, `prepareWhenReady()` and `finishWhenReady()`; `WAIT` means observe later. The real test imports a demo, runs CS2/encoding, checks the visible completed output and saved-folder access after reopening, and ensures website reports stayed unchanged. A separate `cancel()` / `confirmCanceled()` path requests a safe stop and waits for the current engine step to finish; it does not assert immediate termination. Actual footage POV/X-ray/timing still requires inspection; the driver does not pretend accessible button/file checks verify video content.

### Single-action demo analysis and advanced video review

Save a Gemini key once, then select **Analyze demo with Gemini** on the main window and choose a local `.dem`. The button itself is the upload authorization. The app imports the recording, captures a fresh kill-centered clip for every retained eligible opposing-human kill, verifies the complete new set, and sends all bounded batches (at most ten clips and 12 MB of video per request), including available game audio and telemetry. Every batch must pass structured-response and citation validation; if one fails, no combined review is accepted. Accepted batches are checkpointed so a later retry can resume without sending them again. The app displays and saves one combined unverified report only after all batches succeed. The **Exact request preview** in **Evidence** shows the current request structure with MP4 base64 replaced by placeholders; it begins with an estimated size and later shows the exact byte count and hash. Website checks/results are not changed. The model is configured in **API Keys**.

Video responses are accepted only when every observation and suggested moment cites a supplied clip for that alias and a timestamp within that clip's duration. Requests include an explicit alias-to-clip/duration map. Gemini can still return invalid citations; those responses are rejected rather than shown as a completed AI review, and the local demo report remains available. The error identifies an unsupplied clip, a clip assigned to another POV, or an out-of-range timestamp. These safeguards cannot guarantee a valid response or factual observations.

The visible action disclosure explains that identifiable footage goes to Google and quotas/charges/data-use terms apply. A saved key and installed portable capture tools are prerequisites. New capture also needs Steam/CS2 installed, CS2 closed and sufficient disk space; it can take several minutes. If CS2 is already running, **Analyze demo with Gemini** and advanced local capture show a warning before starting; close CS2 yourself, dismiss the warning and try again. Nothing is uploaded or replaced by this blocked attempt. During capture, **Stop after current step** waits for safe engine cleanup, then prevents later upload. During preparation/sending, Cancel stops remaining work but cannot retract data already delivered. Errors stop the chain without automatic retries or fallback. Reports are committed only after complete local saving; canceled saves may leave `.pending` files, not completed reports.

Full per-kill recording can take well over 20 minutes. The capture engine records all raw sequences before encoding MP4s, so an empty MP4 folder during recording is not evidence of a stall. Indexing keeps its 20-minute limit; recording/encoding allows 20 minutes for up to ten clips, plus 30 seconds per additional clip (109 clips: 69.5 minutes). This is a safety deadline, not a completion-time estimate or a guarantee. While waiting, the app reports the phase, elapsed time and deadline every 15 seconds; this is not verified per-clip progress. No Gemini upload begins until the complete capture is verified and upload is confirmed.

For advanced local inspection or isolated diagnostics, the separate workflow remains:

1. Import a demo, capture local clips, then select **Preview Gemini video review** in **Advanced video tools**. Preparation is local and sends nothing. A version-3 manifest binds the original demo and each captured clip by SHA-256/size, exact kill-focused capture plan and relative paths. Older captures without matching source provenance or the current plan must be recaptured; they are never guessed to belong to an imported demo.
2. The app creates separate 960x540/30-fps H.264/AAC review copies, strips container metadata and verifies dimensions, frame rate, duration and hashes. **Open selected preview clip** permits local inspection. Lossy encoding and requested 10-fps model sampling can miss fast/fine details; sampling is not a validated aim-analysis rate.
3. Inspect the Google destination, model, clip labels, byte counts and hashes. The text preview displays the JSON structure with **only base64 video bytes replaced by placeholders** and estimates the request size; immediately before each upload the app verifies the preview-copy hashes and materializes that batch's exact request/hash. Changing model invalidates the preview.
4. With a saved Gemini key, select **Send all prepared batches to Gemini**. This action is the explicit upload authorization; all prepared requests are sent automatically. Opening this advanced window and preparing clips remains local. Transient 502/503/504 failures receive bounded retries, but there is no model fallback or separate Files API session. Canceling cannot retract data already received by Google.

**Video is NOT anonymized.** Names, avatars, map/HUD text and game audio can remain visible/audible despite player voices being disabled during capture. Explicit roster identities, source filenames/paths and raw demo bytes are not added as text to the request, but this does not remove identities from footage. Normal provider retention/data-use terms, quotas and possible charges apply, including free-tier product-improvement terms. Do not send recordings you are not authorized to share.

Each `generateContent` request includes at most ten clips plus the existing bounded identity-stripped telemetry. Every review copy is at most 2 MB, combined binary at most 12 MB and complete UTF-8 request at most 18 MB (decimal limits); oversized requests fail explicitly. Larger clip sets are split into multiple requests without intentionally omitting clips. Each request is materialized and hash-checked immediately before sending to avoid retaining every base64 payload in memory. The video-request deadline is 180 seconds, with existing 128-KB response and 64,000-character structured-text limits. Output allowance is 6,144 plus 384 per supplied player, capped at 16,384 tokens. Selected clips do not cover every fight or the whole match.

For an isolated media test, select **First clip only (video-only diagnostic)** and prepare a new preview. The app still verifies the source-bound capture plan and selected file, but creates/sends only the first captured clip. Only that clip's descriptor and POV alias roster accompany the media; aggregate demo telemetry, event timelines and other player summaries are omitted. The same video-observation schema and strict local parser apply, with a 2,048-output-token ceiling and a one-player local result table. Changing model or clip scope invalidates the preview. This is not the normal all-player review or a full-match quality test; footage remains identifiable.

For a controlled event-context comparison, also select **Include first clip's local event context (no aggregate telemetry)** and prepare again. This adds only that clip's retained own-player shot/kill/death timeline; aggregate telemetry and other player summaries remain excluded. The same one-clip bytes, observation contract, 2,048-token ceiling and strict validation apply. The local measured-basis text discloses retained event counts, not exhaustive counts or verified video timestamps. Events do not establish what is visible/audible or validate an AI claim. Changing either scope option clears the preview; disabling first-clip mode also clears its event-context option. The normal multi-clip workflow is unchanged.

Each validated request result retains the detailed sections and locally identity-mapped player table; a multi-request saved report includes each completed batch with its request and clip provenance. Gemini returns concrete observations and optional review moments, **not broad player statuses or generic normal-play summaries**. Every supplied clip requires exactly one **timestamped video observation**, even when no review moment is suggested: an own-clip number, in-range seconds, visible/audible/not-discernible basis and concrete scene detail or specific limitation. Audio claims require an actual audio stream. Selected clip rounds are disclosed separately from broader telemetry rounds.

Gemini is asked to review the supplied soundtrack and timestamp relevant, discernible game sounds separately from visible details. The report lists how many clips had verified audio tracks and how many audible observations Gemini reported. Track presence does not verify its content, teammate comms, what a player actually heard, or whether the AI's description is accurate. The app does not intentionally capture teammate voices in the standard workflow.

The app derives video table labels from supplied coverage, the model's declared discernibility and structurally valid optional moments: no own POV or entirely not-discernible observations means **Insufficient data**; accepted AI-proposed bookmarks mean **Review suggested**; otherwise **No AI moment suggested** means only that Gemini did not suggest a moment in the short supplied POV. It is not a clean-play finding or clearance. Each suggested moment has its own short rationale. These are review-workflow labels, not model player classifications. Citation validation does not establish a useful review rationale or corroborated suspicion.

Video coverage, conditional alternative explanations and missing-evidence limits are entirely app-authored. The video response root contains only `players`; legacy AI `commentary` or other unexpected fields are rejected, not silently ignored. Telemetry-only reviews retain their existing commentary contract. Per-player AI observations can still contain factual errors and require verification.

Suggested review citations must identify their own clip, in-range clip-relative seconds, recorded round and nominal clip-start tick. Clip-relative timestamps are approximate; clip-start ticks are bookmarks, not precise event alignment. Responses missing scene observations or containing certain known unsupported normality/absence-of-anomalies phrases are rejected rather than displayed as completed reviews. This limited language guard is not semantic validation: structure/citation checks still cannot verify what the model claims it saw/heard or catch every misleading interpretation. Visible/audible observations must be distinguished from inference; no cheating probabilities, accusations or clean-play findings are authorized.

New previews also include locally matched own-player shot/kill/death `EventTimeline` context for each clip. Offsets are nominal, not frame synchronization. The prompt requires uncertain camera attribution around deaths, and the app renders a **local camera-attribution caution** for every retained own-player death inside the planned clip, independently of model wording. Shot events are eligible firearms; kill/death events include any recorded weapon. An empty timeline does not establish survival/no firing, and the caution does not verify the actual transition frame or automatically reject/validate an AI description.

For each clip cited by an AI-proposed bookmark, reports show a **local clip event evidence** ledger alongside the AI reasons. This app-authored ledger lists up to 12 evenly distributed retained own-player shot and kill events and 12 death events, with shown/retained counts, exact demo ticks and nominal offsets; kill rows include the locally mapped victim alias and weapon. It distinguishes a timeline not supplied from a supplied timeline with zero retained events. It does not select a nearest event, align an AI timestamp to a demo tick, verify visual/audio claims or change review statuses. Firing does not establish target absence, intent, abnormality or a useful reason to review. Independent human usefulness validation remains necessary; another AI pass or matching event is not a substitute.

The video JSON schema retains required fields/types/enums but omits numeric/string/array bounds from Google's generation grammar to limit nested-schema complexity. The prompt states these limits and the local parser still strictly enforces roster counts, text lengths, observation/citation caps and actual clip timestamp ranges before accepting a result. There is no automatic retry with weaker validation.

Successful commentary is saved beside its preview copies as `video-review-<unique-id>.txt`, with request hash/destination, source-demo hash, exact review-copy hashes/sizes and **locally mapped recorded names/SteamIDs**. These private review folders must not be redistributed. Results remain separate from website screening and do not change its evidence or conclusions. No raw mouse input, missing subtick commands or original player video is recovered.

**Simplified real desktop E2E:** load [VideoDesktop.e2e.js](scripts/VideoDesktop.e2e.js), call `begin(target, authorizedDemoPath, true)`, then `selectDemo()`. The main Analyze action is the upload authorization and the automated workflow proceeds through preparation and delivery. Use the advanced capture-only and separate-preview methods when testing the local-only path without an upload. Do not authorize unattended live test uploads. Mock transport/schema tests are complementary, not proof of live model processing or factual accuracy.

### Offline video observation benchmark (no API calls)

[Test-VideoReviewAccuracy.ps1](scripts/Test-VideoReviewAccuracy.ps1) audits actual saved scene descriptions against **reviewer-supplied visual/audio judgments**, not keywords or model self-scoring. It runs locally on Windows PowerShell 5.1 without CS2, a key or another upload. Keep the report in its original preview folder with `clip-<number>.mp4` files and the source-bound capture manifest two parent folders above.

```powershell
$report = 'C:\path\to\capture\gemini-preview\id\video-review-id.txt'
$folder = Split-Path $report -Parent
powershell.exe -NoProfile -File scripts\Test-VideoReviewAccuracy.ps1 -ReportPath $report -CreateAnnotations "$folder\accuracy.annotations.json"
# Review the actual media and fill in the generated annotations before evaluating:
powershell.exe -NoProfile -File scripts\Test-VideoReviewAccuracy.ps1 -ReportPath $report -AnnotationsPath "$folder\accuracy.annotations.json" -OutputPath "$folder\accuracy.result.json"
```

The template pins report/request/manifest/source hashes, review-copy hashes/sizes and **every** timestamped description. Do not edit the copied claims or remove entries. Set `reviewerKind` to `human` or `assistant_visual` accurately. Judge each **whole description** as:

- `supported`: all factual/action claims are supported at the cited time.
- `contradicted`: at least one clear factual/state/timing conflict.
- `unverifiable`: available evidence is insufficient, ambiguous or implies unobservable intent; this does **not** mean false.
- `unreviewed`: leave untouched until assessed; never counted as a pass.

Every assessed entry requires a `reason` and at least one `references` object containing `path` (relative to the report folder), uppercase `sha256`, `kind` (`frame`, `sequence` or `audio`), `startSeconds`, `endSeconds` and an observable `fact`. Frame references are PNG/JPEG files with equal start/end offsets within 0.1 s of the claim; sequence/audio references must be the cited retained review MP4 and their reviewed intervals must contain the claim time. For example, extract a reference with bundled FFmpeg using `-i clip-4.mp4 -ss 0 -frames:v 1 -an reference.png`, then hash it with `Get-FileHash`. For motion/bursts/tracking, review the actual surrounding sequence and cite its MP4 and reviewed interval; **one still cannot prove continuous motion, tracking, player intent or the absence of a shot**. Audible claims require audio references. The runner validates hashes/paths/times, but cannot prove the annotation or a reference's asserted origin is truthful.

Output reports raw counts, reviewed/total and supported/total denominators. Exit `0` means only that all descriptions have supporting annotations and retained-copy provenance matches the report; `2` means incomplete, issues found or legacy provenance unverified; invalid/tampered input fails with an explicit error (`1`). Output files are create-only: use a new result filename for another run. Older reports without saved copy hashes remain explicitly `legacy_folder_association_only`; matching a folder never retroactively proves the original request's video bytes.

This is **not automatic semantic validation, cheating-detection accuracy, a player verdict or independent human ground truth**. It scores scene descriptions, not review-moment rationales, telemetry or global notes. The initial private baseline uses the existing real ten-clip report and exact-time frames: one whole static description supported, one planting-state conflict, eighteen descriptions needing sequence/intent verification. That is a still-frame audit, **not a 5% model-accuracy result**. Do not publish private footage, reports, annotations or frames.

Run the reusable accounting/integrity regression cases with:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts\Test-VideoReviewAccuracy.Tests.ps1
```

These synthetic runner tests cover denominator preservation, changed claims/media, timestamp/path validation and legacy provenance. They do not measure actual model accuracy. The players-only video contract is locally tested; a fresh live generation test requires separate, specific Google-upload approval.

**Metric definitions and provenance:**

- **App-calculated core ratios:** CSTracker match-history K/D is pooled `sum(kills) / sum(deaths)` over verified unique rows, never an average of page K/D values. CSTracker detailed K/D uses its displayed lifetime kill/death totals; detailed headshot-kill percentage is `100 * headshot kills / kills`. CSTracker profile win rate is `100 * wins / (wins + losses)`, so ties are excluded. Leetify public-feed values are converted only where their contract requires it (for example a win-rate fraction is multiplied by 100). Zero or missing denominators remain unavailable; they are not converted to zero or infinity.
- **App-calculated optional ratios:** csst.at opening-duel win rate is `100 * won / (won + lost)` and is checked against the displayed percentage. Weapon accuracy spread is the maximum minus minimum qualifying per-weapon accuracy; CSTracker uses its displayed percentages, while Steam uses `100 * hits / shots` from official counters. Map outlier ratio is the best qualifying map K/D divided by the median K/D of the remaining qualifying maps. Oscillation values are pooled K/D per complete consecutive block of CSTracker matches. Utility damage per match is source-reported and compared only when K/D from that same detailed sample meets the configured gate.
- **Source-calculated/displayed values:** Leetify recent K/D, headshot-kill percentage and win rate; csst.at Scope K/D and K/R; CSTracker time to damage, preaim, aim offset, HLTV rating, KAST, ADR and accuracy are accepted from the source feed/website. The app validates their shape, range, unit and any independently available totals, then applies the site's published cutoff and direction. It does **not** claim to reproduce provider-specific event aggregation, shot eligibility, reaction timing, KAST, ADR, rating, population-percentile or benchmark formulas when the raw underlying events are unavailable.
- **Definitions visible in reports:** K/D is kills per death; headshot kills are the fraction of kills credited as headshots, not head accuracy; K/R is kills per round. CSTracker labels TTD as time to damage, without publishing enough event-selection detail to independently reproduce it here. Preaim and aim offset are provider-defined angular measurements in degrees; HLTV rating is CSTracker's displayed provider value; KAST is the provider's percentage of rounds with a kill, assist, survival or trade; ADR is provider-defined damage per round; accuracy is the provider's shot/hit-derived percentage. Provider definitions and event eligibility can differ, so equal-looking units across sites are not automatically equivalent.
- **Unscored context:** extra details such as flash assists, enemies flashed, flash duration, grenade use, trade/first kills, enemy/team damage, unused utility, spray accuracy, spot-to-damage/kill, counter-strafing, AFK behavior and hit-group distributions are retained as source-reported context. They do not enter a rule or the verdict unless a named rule is explicitly documented. Overall accuracy, head accuracy and spray accuracy must not be read as headshot-kill percentage.
- **Public-tab denominator differences:** CSTracker breakdown tabs can report a different eligible-event scope or denominator from the detailed combat total. For example, a kill-category breakdown may publish 2,639 eligible category events while the detailed aggregate reports 2,620 kills. The app preserves both as attributed provider values, adds an explicit caveat, and never reconciles or adds them together. Only named calculations using a verified same-sample denominator feed screening; inconsistent-looking contextual totals are not silently corrected.

Final result lists K/R separately by source, with the relevant match or counter sample and scope limitations; it does not merge them or imply they are directly comparable. When Steam reports its separate match-total counter, the K/R line shows it as context only, not as the verified match count for the K/R counters; missing or invalid match totals remain unavailable. Evidence describes optional-check eligibility and why a check was not assessed when its source data or minimum sample is insufficient. A check that was not assessed is not a pass.

**Steam lifetime K/R is context only.** Its kill and round counters are not established to cover matching modes or periods, so their ratio is displayed without applying the K/R warning line. It cannot trigger a cheating indicator, contribute to metric coverage, or raise batch review priority; a source returning only this ratio is not counted as assessed gameplay data. Valid source-scoped match-based K/R, including csst.at's displayed Scope value, remains screened under the configured K/R rule. Other Steam metrics and weapon checks retain their existing behavior. Steam's ratio and raw counters remain visible in both reports, including when no other Steam gameplay metric is available.

This is a heuristic statistical screener, **not a trained cheating detector**. It uses four core app rules (K/D, headshot %, win rate, kills per round), pattern screens derived from public tables, and available website-published cutoffs for aim/reaction measurements. The values below are the **defaults**; users can change app-defined thresholds and sample requirements in the Screening rules tab:

- **Weapon accuracy variance:** across weapons with at least 100 kills and 1,000 shots (three or more required, spanning **at least two weapon categories** — same-category rifles legitimately cluster within a few points), a hyper-narrow accuracy spread (under 3 percentage points) is flagged. CSTracker's spread uses its displayed percentages, which may be rounded; Steam's uses returned shot and hit counters. Grenades, knives, and small-sample weapons never qualify. The section also reports the sniper kill share, since AWP/Scout mains legitimately reach 45-55% overall accuracy.
- **Utility-to-frag disconnect:** when the lifetime detailed sample shows K/D of at least 1.5, utility damage under 30 per match is flagged. Role, modes and play style can explain the combination; it is not evidence of wallhacks.
- **Recent-vs-lifetime K/D jump:** when CSTracker's recent-window K/D is at least 1.8 and exceeds the same website's lifetime K/D, a jump of 0.75 or more is flagged. Both windows come from the same website; no cross-site mixing. These overlapping averages do not establish when or why performance changed; improvement, opponents, modes and selection bias can explain the difference.
- **Opening duel win rate:** from csst.at's Scope panel (won/lost first-engagement counts verified against the displayed rate), a win rate of 70% or more across at least 100 recorded duels is flagged. Below 100 duels it is context only. Skill, positioning and team support can explain high rates; this does not establish pre-information.
- **Performance oscillation:** the retrieved CSTracker match history is split into consecutive blocks of ten matches (pooled raw kills/deaths per block, at least five complete blocks required, up to 50 blocks across the 500-match window). The screen flags when at least two blocks reach K/D >= 2 **and** at least two blocks sit at K/D <= 0.6 in the same history. It counts extremes, not their alternation, and cannot detect toggled assistance. Form, opponents and modes can produce both extremes.
- **Map K/D consistency:** across maps with at least 20 matches (three or more required), the screen activates only when the best map reaches K/D 1.5+, and flags when that map is at least twice the median of the player's other maps. Comfort-map skill, opponents and modes can explain even a flagged gap.
- **Headshot flagging floor:** the headshot core rule can only flag on samples of at least 10 matches (when the count is known); smaller samples still display the value but a single pop-off game cannot trip a core indicator.

No-flags results do not prove clean play, and flagged results are reasons to review demos, not cheating verdicts or probabilities. There is deliberately **no cumulative suspicion percentage**: summing uncalibrated heuristics into a confidence score would be false precision. The utility and win-rate rules inherit whatever modes the source website tracks; that scope limitation is theirs, not evidence. Steam's export also supplies a **limited (free) account** marker as context only — it describes many legitimate new players and is never scored. Deliberately rejected ideas: eco-round splits and crosshair-smoothness analysis (no public per-round or tick data; nothing is invented) and teammate ban-rate clustering (guilt by association). Browser rendering is always enabled in the desktop app.

**Smurf-review context (not scored):** Final result and Evidence show Steam account age in days from a verified public membership date, Steam community level from the optional keyed `IPlayerService/GetSteamLevel/v1/` request, and available public-profile Leetify Premier rating and Competitive map ranks (numeric 1-18, separately per map). Each source is attributed with its retrieval time; age includes its UTC calculation date. Rank update times are not established, so a recently retrieved rank is not presented as current. Missing/private fields, zero rank placeholders, invalid values and ambiguous duplicates remain explicitly unknown; a genuine Steam level zero is retained. An unavailable level or rank does not discard independent valid data. Without the relevant API key no extra endpoint is requested. Steam level measures community progression, not CS skill or CS profile XP level; account age is not time played. No CS profile XP level is collected. These fields do not affect metric coverage, cheating flags, account cautions, or batch review priority. There are no automatic smurf thresholds or probabilities: a reliable rank-matched performance baseline has not been established.

**Screening rules tab:** the explanations alongside the settings describe each comparison, sample requirement, rationale and limitations. Relevant examples from the existing professional-stat snapshot appear within the rule descriptions as context, not as a calibrated basis for the thresholds or a live update; there is no reference for every rule. Blank lines group the JSON settings in the same order as the rule descriptions; both sides scroll independently. Edit numeric values in the JSON editor, then select **Save rules**. Keep every field, use a decimal point, and enter percentages from 0 to 100. The comparisons, data validation, ban cautions and website-published cutoffs are not editable. **Restore defaults** fills the editor with the original values; save them to apply. The app validates all values before saving to `screening-rules.json` in the user's CheaterOrNot application-data folder, separately from API keys. If saved rules cannot be read or validated, checks are blocked until the rules are corrected or defaults are saved. A check uses one saved rules snapshot for all players; changes apply only to future checks and never rewrite a displayed report. Evidence records the exact app settings used; website cutoffs remain labeled and take precedence over a duplicate core rule within the same sample. Changing a threshold does not make it validated or turn the result into a cheating determination.

**Professional context on flagged metrics:** Final result can quote up to three cached **Top Pro Players** account examples from the same provider, panel, metric and unit, excluding the checked account. It selects the nearest known match counts, prints the sample sizes and retrieval dates, and marks data over 24 hours old. Where a supported metric lacks matching samples, the report says so. Tournament, FACEIT lifetime, and other unmatched samples are not substituted. No extra network request is made, and refreshing the tab does not rewrite a completed report. These examples help interpret flags; they neither change nor validate the screening rules, verdict, or batch ranking.

**Account ban history is surfaced as a visible caution, separately from the statistics.** When CSWatch reports Steam bans on record (which can include game/Overwatch bans) or Steam's own VAC flag is set, the Final result shows an **ACCOUNT CAUTIONS** section naming the source and finding, even when no statistical indicator fired. Steam's ban status is public regardless of profile privacy, so the VAC flag is read for private/friends-only accounts too; game bans are not in Steam's XML export, so CSWatch's ban count covers those. Cautions raise review priority but are never scored as statistical indicators: a historical ban may concern another game and is not proof of current CS2 cheating.

The **Evidence tab is kept lean**: each checked source shows its URL, retrieval time, data, identity-verification and sample-scope notes, and real access errors. Shared caveats appear once in the header/footer. The Final result notes TrackBans separately as not checked.

CSTracker's public context tabs use layout-aware plain text: website section-number badges (03, 04, etc.) are removed; each kill-breakdown item and clutch scenario has its rate/counts on one line; each map and weapon has one record line with fields separated by ` | `; detailed statistics retain one label/value line per measurement. This is display-only formatting; extracted metrics, samples and scoring are unchanged.

The default window is 1360 logical pixels wide. Evidence preserves report lines without soft wrapping and offers horizontal scrolling for rows longer than the available width; Final result retains paragraph wrapping. Public-tab records have no empty lines between entries; section headings remain separated.

The progress bar appears as soon as a valid check starts. It shows the current website, completed website checks, and the number of usable performance summaries obtained. A failed, blocked, or empty website counts as a completed attempt, **not** as usable data. Unsupported catalog entries are not counted as website checks.

Leetify's verified public website feed is checked first, before slower HTML/browser sources. The final progress step closes Chromium, removes temporary browsing data, and prepares the report. The bar reaches completion only after that succeeds. Cancellation shows the cleanup stage and does not report an interrupted check as successful; cleanup failures are explicit.

The report appears after browser cleanup. The bar measures completed work, not elapsed time, cheating confidence, or the percentage of websites successfully supplying data.

## Public sources and actual coverage

- **Leetify:** verifies `steam64Id` from anonymous public profile metadata before fetching the webpage's recent 5v5 overview. Uses the returned match count, K/D, headshot kill percentage, and win-rate fraction converted to percent. Does not use lifetime totals, population benchmarks, or head accuracy as the player's headshot percentage. The website feed is an observed frontend data contract and can change. No official developer/profile API is called.
- **csst.at:** preserves the identity-verified Scope K/D and K/R from the original anonymous browser navigation HTML when already present, before scripts can replace the panel. For an incomplete original panel it waits for both metrics, retaining the original partial panel if a complete one does not appear. It does not make a separate HTTP-client request or retry a refusal. If the panel requires JavaScript, the browser waits for that specific panel rather than an unrelated provider card. Excludes trend deltas, other provider cards, and side/weapon tables. The panel's sample is the Scope card's own published window (for example "Last 15 matches") when present; otherwise it stays unknown rather than borrowing a different provider's match count. K/R is the displayed value; underlying kills and round counts are not independently verified.
- **CSTracker:** verifies the Steam profile link or explicit profile-owner SteamID attribute, then follows verified same-player older-match links for up to 25 pages (about 500 matches), which also deepens the oscillation screen's window; lifetime K/D and headshot totals come from the details tab and already cover the full tracked history without pagination. Pools raw kills/deaths across unique match rows; never averages page K/D ratios. Also reads the public profile result totals and the **separate recent analysis panel**: TTD, preaim, aim offset, K/D, HLTV rating, KAST, ADR, accuracy, population benchmarks and warning-cutoff metadata. These published cutoffs now participate in the assessment, labeled as website-defined heuristics. Accuracy is not headshot percentage. The **Detailed stats** section supplies its own match count, raw kills/deaths/assists and headshot kills; these compute a separate K/D and headshot kill percentage, validated against the displayed percentage's precision so the site's rounded or truncated display is accepted without allowing materially conflicting values. Its displayed win rate is retained as unscored context; the header's separately assessed win rate excludes ties and uses only decided matches. The detailed totals, recent panel and returned history are never combined into a fictitious sample. Where CSTracker explicitly publishes a profile synchronization timestamp, the report records it separately from retrieval time; equivalent samples prefer the newer timestamp, while larger/non-comparable samples and different websites remain separate. Utility, team-behavior and extra aim fields from the public tabs remain in Evidence as unscored context and never become screening flags merely because they are present. Duplicate matches or mismatched identities reject the affected match sample. Invalid history or older-page failures retain independent verified sections and any earlier verified history with an explicit partial-retrieval warning. K/R is not invented without a round count.
- **CS2 progression context:** CSTracker's identity-verified header and rank history can provide a demo-observed Competitive rank per map, CS2 profile level/progress, and the currently displayed annual Service Medal year. These fields appear under the unscored smurf/account context and do not affect coverage, flags or review priority. The public page does not publish a trustworthy lifetime list/count of all Service Medals, so the app reports prior years and total medals earned as unavailable instead of treating repeated medal icons as separate awards. Rank values are source-attributed observations, not live Valve certification, and include the latest observed date where the rank chart supplies one.

**CSTracker rolling recent windows:** the match-history “When” tooltip's exact `played yyyy-MM-dd HH:mm` timestamp is parsed together with the unique match identity and raw K/D/A counters. Evidence then computes cumulative rolling 7, 14, 21, 28, 35, 42, 49 and 63-day UTC windows ending at retrieval time, using pooled kills/deaths rather than averaging match ratios. The windows overlap and are never added together. CSTracker's larger history remains the source's selected K/D assessment, while the recent windows remain visible as source-attributed trend samples and are summarized separately in Final result.
- **CSStats (not an automatically checked source):** CSStats was removed from the automatic check because every scoreable metric it publishes — K/D, headshots, win rate, KPR, ADR, KAST, HLTV, per-weapon accuracy, per-map performance, clutches — is already retrieved from CSTracker, Leetify, and csst.at, so it added only a duplicate/overlapping sample and Cloudflare-blocked noise. Its public stats sit behind a Cloudflare **bot-verification** checkpoint that deliberately refuses the app's automation-controlled browser (it keys on `navigator.webdriver`) while a genuine human browser passes without interaction. The app does **not** defeat that detection — hiding automation flags, forging a browser TLS fingerprint, reusing a human's `cf_clearance`, routing through a third-party unblocking API, or adding account credentials would all be impersonation/circumvention, and credentials would not help because the data is already public and the block is on automation, not login. A `csstats.gg` profile URL is still accepted as **input** (its SteamID is extracted and the other sources are checked).

#### When automated access is blocked: open it in your own browser

Whenever a checked public gameplay page (csst.at or cstracker.gg) returns no automated statistics, the app shows an **"open it in your own browser"** button that launches that exact public page in your real default browser, where the site's own checks clear naturally because it genuinely is you. This is view-only context; the app does not scrape the result back, so no reports change and no personal session is stored.
- **CSWatch:** extracts identity-verified public account tiles (Steam bans, community reports, account age, CS2 hours when supplied). This account context is CSWatch's unique contribution: its community-report count exists nowhere else, and its ban/account fields often remain visible when the Steam profile itself is private. A **Private profile** Steam badge no longer discards other publicly visible account tiles. Its gameplay mechanics panel is **Leetify-derived ("via Leetify") and deliberately not imported**: the Leetify source already represents that data, and scoring it again would double-count one origin as two independent sources. Does not import its risk score or treat community reports as verified cheating detections. No comparable gameplay sample is established.
- **Steam:** retrieves the anonymous Steam Community public profile XML and verifies exact SteamID and privacy state. This is the **authoritative record for the VAC-ban flag and membership date** (other sites only mirror it), and its privacy state lets reports explain missing data honestly rather than leaving a hole. A public export can supply the VAC-ban flag, display name and membership date. A private/friends-only export can also provide a publicly returned display name and VAC status; other private account details are not imported. An unrecognized membership date is reported without discarding the name or ban status. This differs from what an authorized owner/friend may see in their own browser. This is not the keyed Steam Web API. A flag is not a game-specific ban count or proof of current cheating. External XML entities and DTDs are prohibited.
- **Leetify API (official, keyed, optional):** only when you save your own free [Leetify developer key](https://leetify.com/app/developer) in the **API Keys** tab, the app also calls Leetify's official Public CS API `/v3/profile` endpoint: lifetime tracked-match count and win rate (a separate sample from the recent-matches website panel, never added to it), **platform ban records** (for example FACEIT bans, surfaced as account cautions with dates), and Leetify-computed aim telemetry (preaim, reaction time, head accuracy, spray accuracy) shown as unscored context because no published warning cutoffs exist for those API values. For profiles identified as public, it also requests `/v3/profile/matches` and groups returned, identity-verified matches into separate 7-day and 15-day UTC calendar views. Windows within each view do not overlap, but the views overlap each other and must not be added together. Evidence shows pooled K/D, K/R, headshot-kill percentage, reported damage per round and map/source counts as **unscored context**. Each ratio uses only matches with its necessary valid counters and shows its own sample count; the API's rounds and damage scope has not been independently verified. Small samples are volatile, and the API's returned history may be incomplete. Missing periods are not assumed to be no play. This history is separate from other sources and does not change the verdict. Match history has a separate 16 MB response limit; exceeding it or other request errors are reported without discarding the profile. Both views use the same response, so seven-day windows do not reduce download size. The integration has fixture tests but has not been validated with a live keyed response. A profile request returning HTTP 404 does not establish why it is unavailable; the public website and official API can have different coverage. The key is sent only as a request header to `api-public.cs-prod.leetify.com`; identity is verified by matching the returned SteamID. Usage follows Leetify's developer guidelines, including the in-app "Data Provided by Leetify" attribution.
- **FACEIT Data API (official, keyed, optional):** a [FACEIT developer account and Data API key](https://docs.faceit.com/docs/data-api/) enable lookup by SteamID, followed by a CS2 lifetime-statistics request. The app verifies the linked SteamID and the returned FACEIT player and game IDs. Recognized match, win, win-rate and K/D fields are shown as **unscored FACEIT context**, separate from other samples: their exact aggregation and sample definitions have not been independently verified. A player-lookup HTTP 404 is distinguished from a statistics HTTP 404: if the account is verified but CS2 lifetime statistics return 404, the account context is retained and the missing statistics are reported explicitly. This is not a missing account, zero-match count, or passed screening check. An unmatched account, invalid response, authorization failure or rate limit is reported without inferring data. The key is sent only as a bearer header to `open.faceit.com`. An authorized live diagnostic verified SteamID lookup and the separate statistics-404 case; successful lifetime-statistics parsing is covered by fixtures, not a live response.
- **Steam Web API (official, keyed, optional):** only when you save your own free Steam Web API key in the **API Keys** tab, the app also calls Valve's official `GetPlayerBans` endpoint (account-wide VAC-ban and game-ban **counts** plus days since the last ban, available regardless of profile privacy — game bans can concern other games as well as Overwatch convictions; the app does not identify which games) and `GetUserStatsForGame` for app 730 (lifetime kills, deaths, rounds, headshot kills, matches, time played, and per-weapon shots/hits that feed a context-only kills/rounds ratio and a second weapon-accuracy-variance screen) when the player's game details are public. Valve's lifetime totals are account-lifetime and can include CS:GO-era play; the report labels them as long-run context. Ratios are calculated independently when their required counters are valid; missing, invalid, or duplicate counters are not substituted. The API does not establish that these counters cover the same modes or periods, so their ratios may not be comparable to match-based metrics. The reported match total is not assumed to describe K/D, headshot kills or K/R: Final result shows K/R's reported kills and rounds while noting that its match count is unverified. The lifetime kills/rounds ratio is not assessed, contributes no screening coverage, and receives no professional comparison. Identity is verified by matching the returned SteamID. Without a saved key, none of these endpoints are contacted.
- Steam statistics HTTP failures are reported by status without asserting an unverified cause. An HTTP 400 can have multiple causes, including private game details or unavailable statistics; HTTP 401/403 indicate authorization/access failures, and HTTP 500 is a server error. The verified ban record remains separate. The app does not display raw error bodies or key-bearing request URLs.
- **TrackBans (not checked):** the checker reported maintenance when reviewed on 2026-11-16 and has no verified automatic adapter. The app does not submit player IDs to it. Its advertised probability is not imported.

Without a saved key there are no official Leetify, Steam Web API or FACEIT API calls. Anonymous website JSON and Steam's public XML are still public website data; JavaScript-driven websites commonly use data responses instead of putting statistics in their initial HTML.

Universal performance coverage remains unavailable: private profiles and access challenges can block data, and sources not listed as checked are not integrations. The app does not infer performance from an error page, substitute rank/season counters, or turn account/ban context into gameplay evidence. Retrieval timing and coverage are not guaranteed.

### Crawling linked data rather than only the landing page

CSTracker's Profile, Stats, Kills, Details, Clutches, Maps, Grenades and Weapons tabs are same-document anchor sections on the inspected public profile, not separate server pages. The renderer retains those published gameplay sections, not only the match table. Their additional tables/text appear in Evidence with their own headings and website-stated scope. Detailed tables are excluded from Final result to keep its assessment readable. Chat, location, unrelated-player pages and login/sync actions are not crawled. Large SVG/chart drawing data is excluded without dropping the adjacent numeric measurements or raising size limits.

Separate public responses still require source-specific adapters: CSTracker's observed older-page links are followed up to 25 pages; Leetify's verified public website responses are read separately. Robots policies, identity checks, cancellation and request limits still apply. This is **not** unrestricted recursive crawling — unbounded full-history pagination is deliberately avoided out of respect for the websites, because very old matches decay in relevance for current-cheating review, and because lifetime aggregates already arrive through the details tab — and no claim is made that every subpage of every catalogued site has a working parser.

Regression fixtures cover separate profile totals, recent telemetry, detailed combat aggregates and website trust ratings without embedding real account identities. Extraction projects the verified match-history section and exact profile-owner identity, excluding unrelated charts without raising limits or truncating match rows. Trust ratings remain unscored context, not Valve Trust Factor or cheating probabilities.

CSTracker benchmark diagnostics distinguish duplicate labels, unrecognized title formats, and invalid percentile/sample values. An unrecognized format is not proof the website supplied invalid data: the measurement and valid cutoff remain available, while the benchmark stays unavailable until its format can be verified.

The supplied standard Leetify logo is scaled without modification in one compact **Data Provided by Leetify** profile link, shown only when its data is present. The large logo panel, duplicate links, and logo-import controls were removed. The [developer guidelines](https://leetify.com/blog/leetify-api-developer-guidelines/) request a specific attribution badge; full branding compliance has not been confirmed and should be checked before public distribution.

The app does not identify affected games. The public XML export only exposes a VAC yes/no flag; the keyed API adds counts and recency and covers game bans.

The Leetify key contributes the official `/v3/profile` data and, for public profiles, `/v3/profile/matches` 7-day and 15-day trends described above: lifetime tracked matches and win rate, platform ban records as cautions, and unscored aim-telemetry and trend context.

The API Keys tab can test saved keys. Keys do not appear in reports, evidence or app logs. Official APIs are governed by their providers' API terms (robots.txt does not apply to them). Keys are format-validated before storage, and Remove key buttons delete them. Valve's lifetime totals are undated account-lifetime values that can include CS:GO-era play and need not match CS2 playtime, so they are labeled as long-run context rather than current form.

## Temporary data and privacy

**Account identities are runtime input, not repository examples.** Do not add real SteamIDs, account-specific reports, or live-check histories to source, tests or documentation. Automated tests generate SteamID-shaped identifiers at runtime and use mocked HTTP responses or local fixture servers only; they do not look up those identities on live services. Any live-account development check must first ask for the SteamIDs to use, and must not write them into committed files. Steam's numeric format/range constants describe the protocol, not selected player accounts.

The repository ignore rules exclude build output, test results, portable publish output and local report exports. They do not remove files already tracked by Git; review the staged files before publishing, and distribute portable binaries separately from source.

Each check uses a fresh, **headless** Chromium profile, not your personal browser or saved logins. Page data and anonymous HTTP/JSON responses are processed in memory. Chromium may write cookies, local storage, and cache beneath `%TEMP%\CheaterOrNot-browser-<random>` (or the OS temp directory).

The browser closes and its temporary session directory is deleted before showing the report, including on cancellation and normal app close. Cleanup failures name the directory and prevent a success claim. **Crashes, forced termination, OS failures, or denied deletion can leave files behind.** Deletion is not secure erasure; OS paging and backups are outside the app's control.

Website evidence, result views and local-only demo imports remain in application memory unless exported. **Analyze demo with Gemini automatically sends reconstructed footage plus bounded telemetry to Google and saves the returned unverified report locally.** Advanced video Send also saves its report; diagnostics save redacted outcomes. Local capture persists video files, manifests, diagnostic logs and the capture engine's private demo index under the portable folder. Reports/output contain identities and must not be redistributed with source or portable packages. **Clear player data** clears in-memory views and context; it does not delete original demos, saved reports, capture/index files or delivered Google data. Raw demo files are never uploaded. The app does not scan for demos automatically: a user selects the demo for analysis. No per-send approval controls remain.

Website requests disclose the queried SteamID and your IP; rendered pages may also contact third-party resource hosts. Optional saved API keys are read only for their explicitly configured official integrations and are sent only to the matching provider, as described above.

Chromium's sandbox stays enabled. Robots policies apply to pages, scripts, and data. Valid crawl delays up to 30 seconds are scheduled per origin; disallowed routes, invalid/longer delays, and unavailable robots files (except 404) are declined. HTTP redirects are not followed. Browser navigation is limited to verified same-player routes.

Service workers, downloads, images/media/fonts, non-GET/HEAD requests, WebSockets, and unverified child-frame/navigation requests are blocked. Browser operations have a 35-second deadline, 20-second initial-navigation limit, 12-second summary-readiness limit, 150-request ceiling, 50,000-node extraction ceiling, and 2,000,000-character extracted-HTML limit. These do not cap total browser process memory or network bytes. Access/privacy messages can be recognized before slow page resources finish; remaining failures are reported rather than bypassed.

There is no login automation, CAPTCHA solving, stealth modification, automatic retry, or access-control bypass. The desktop app always uses bundled background Chromium where rendering is needed. The core library retains static HTTP retrieval for callers without a renderer; it does not pretend that static requests have browser-session access.

## How review works

Sources remain separate because trackers can overlap and use different modes, ranks, and time windows. **Every usable sample is assessed tentatively**, with its actual count or an explicit unknown count. A 30- or 90-match sample is not discarded, inflated or combined with overlapping data to meet an arbitrary minimum. Zero-match performance placeholders are rejected. Short/unknown samples require more caution, not silent exclusion.

The four app rules remain K/D >= 2, overall HS >= 75%, win rate >= 80%, K/R >= 1. Additional CSTracker checks compare each measured value with its own published `suspiciousCutoff` and direction: values below a lower-is-suspicious cutoff or above an upper-is-suspicious cutoff are flagged. Equality is not beyond those website cutoffs; app rules retain their inclusive boundaries. Each check identifies its origin. Website cutoffs take precedence over a duplicate app-rule metric within that same panel; different samples still remain separate. One distinct flagged metric type gives a possible-indicator assessment; multiple types give a multiple-indicator assessment. These are heuristic comparisons, not calibrated anti-cheat benchmarks, independent evidence counts, or cheating probabilities.

Missing metrics are labeled as unavailable in their stated sample. Ambiguous HTML summaries, conflicting values, mismatched player identities, and invalid numeric values are rejected; a CSTracker section failure does not discard other verified sections. Public timing/aim statistics can be compared with the website's published cutoffs. Historical blocks and recent-vs-lifetime comparisons are limited statistical summaries, not demo-event, weapon-calibrated, behavioral or recoil analysis. Community/AI suspicion scores are not converted into cheating probabilities.

```powershell
dotnet run --project src\CheaterOrNot -c Release -- --install-browser
dotnet run --project src\CheaterOrNot -c Release -- --prepare-capture-tools
dotnet run --project src\CheaterOrNot -c Release
```

```powershell
$env:PLAYWRIGHT_BROWSERS_PATH = Join-Path (Get-Location) 'src\CheaterOrNot\bin\Release\net10.0\browsers'
dotnet test tests\CheaterOrNot.Tests -c Release
dotnet publish src\CheaterOrNot -c Release -r win-x64 -p:PublishProfile=Portable -o publish

```

Real-browser tests are explicitly skipped unless `PLAYWRIGHT_BROWSERS_PATH` names an installed browser directory; no browser is silently downloaded by tests. Fixture success is not proof of universal live-site coverage.

Each OS/architecture needs a separate executable and matching browser bundle. Only Windows x64 packaging/runtime has been verified here. macOS signing/notarization and Linux packaging remain unverified. On macOS/Linux, use `/` in shell paths; Linux also requires [Avalonia native desktop dependencies](https://docs.avaloniaui.net/docs/overview/supported-platforms) and [Playwright Chromium dependencies](https://playwright.dev/dotnet/docs/browsers#install-system-dependencies). A self-contained executable still needs OS-native dependencies, and Playwright's supported platforms are narrower than the .NET RID list.
